## Q1. Most common file/package structure for a shareable workflow, and standard metadata fields

### Takeaway
The converged shape is a folder bundle whose unit is a Markdown file with YAML frontmatter (SKILL.md, .agent.md, .mdc, workflow .md), optionally wrapped in a plugin folder with a small JSON manifest (`.claude-plugin/plugin.json`) and listed in a git-hosted `marketplace.json` catalog. Metadata is minimal: name, description, plus optional version/author/license; capability fields (tools, model, globs) are product-specific.

### Cited Findings
- Agent Skills open standard: a skill is a directory with required `SKILL.md` (YAML frontmatter + Markdown) and optional `scripts/`, `references/`, `assets/`. Required fields `name` (1-64 chars, lowercase/digits/hyphens, must match parent dir) and `description` (1-1024 chars). Optional `license`, `compatibility` (<=500 chars; env requirements), `metadata` (string->string map), `allowed-tools` (space-separated, "experimental"). — [agentskills.io spec](https://agentskills.io/specification)
- Progressive disclosure: ~100 tokens of name+description loaded at startup for all skills; full body (<5000 tokens recommended) on activation; resources on demand; keep SKILL.md under 500 lines. — [agentskills.io spec](https://agentskills.io/specification)
- Claude Code skills extend the spec with: `disable-model-invocation`, `user-invocable`, `disallowed-tools`, `context: fork` + `agent` (run in subagent), `model`, `effort`, `paths` (globs), `hooks`, `shell`, `arguments`; unknown fields are silently ignored; CC-only fields do not work on claude.ai/API, which accept only spec fields. Variables `${CLAUDE_SKILL_DIR}`, `${CLAUDE_PLUGIN_ROOT}`, `$ARGUMENTS`; dynamic context injection via `` !`cmd` `` (can be disabled with `disableSkillShellExecution`). — [Claude Code skills](https://code.claude.com/docs/en/skills)
- Claude Code plugin = folder with optional `.claude-plugin/plugin.json`; only `name` required (kebab-case; every component namespaced `plugin:component`). Manifest fields: displayName, version, description, author{name,email,url}, homepage, repository, license (SPDX), keywords, defaultEnabled, dependencies, settings, userConfig, channels, skills, commands, agents, hooks, mcpServers, lspServers, outputStyles, workflows, experimental.{themes,monitors,evals}. Without a manifest, standard layout is auto-discovered. — [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)
- Standard plugin layout: `skills/<name>/SKILL.md`, `commands/*.md` (legacy; prefer skills), `agents/*.md`, `hooks/hooks.json`, `.mcp.json`, `.lsp.json`, `output-styles/`, `themes/`, `workflows/*.js`, `monitors/monitors.json`, `bin/` (put on Bash PATH), `settings.json` (only `agent` and `subagentStatusLine` honoured). — [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)
- Manifest rules: all component paths must start with `./`, resolve inside the plugin root and exist (no `..`); unknown top-level keys are stripped with a warning, unknown keys inside strict objects (userConfig, lspServers, channels, monitors) are errors; `claude plugin validate` is the checker. Some keys replace the default dir (commands, agents, outputStyles), skills add to it, hooks/mcp/lsp merge. — [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)
- Marketplace = repo/dir with `.claude-plugin/marketplace.json` (required `name`, `owner`, `plugins[]`; each entry needs `name` and `source`). Source types: relative path, `github`, `git-subdir`, `url` (git), `archive` (zip over HTTPS, optional sha256 pin), `npm`, `command`. Entry may supply the manifest itself (`strict` default true: entry components are appended to plugin.json; `strict:false` with conflicting components fails with "conflicting manifests"). — [Create a marketplace](https://code.claude.com/docs/en/plugin-marketplaces), [manifest reference](https://code.claude.com/docs/en/plugins-reference)
- VS Code custom agent = `.agent.md` (or `.md`) with YAML frontmatter (`name`, `description`, `tools`, `handoffs` [label/agent/prompt/send], `user-invocable`, `disable-model-invocation`) plus Markdown body; full field list in a separate reference page not fetched. — [VS Code custom agents](https://code.visualstudio.com/docs/copilot/customization/custom-agents)
- Roo Code custom mode = YAML object: `slug`, `name`, `description`, `roleDefinition`, `whenToUse`, `customInstructions`, `groups` (read/edit/command/mcp; `edit` may carry `fileRegex` restricting editable paths). Per-mode rules in `.roo/rules-{slug}/` (fallbacks `.roorules-{slug}`, legacy `.clinerules-{slug}`). — [Roo custom modes](https://roocodeinc.github.io/Roo-Code/features/custom-modes)
- Cursor project rules = `.mdc` files in `.cursor/rules` with frontmatter `description`, `globs`, `alwaysApply` (4 behaviours: always / glob-attached / agent-chosen by description / manual @-mention); plain `.md` there is ignored; AGENTS.md (no frontmatter) also supported, nested files combine with specific winning. — [Cursor rules](https://cursor.com/docs/context/rules)
- Kiro steering = Markdown in `.kiro/steering/` with frontmatter inclusion modes `always` (default), `fileMatch` (+`fileMatchPattern`), `manual` (`#name` or slash), `auto` (needs name+description); AGENTS.md supported (always included, no modes). Custom agents do not load steering unless `resources` lists `file://.kiro/steering/**/*.md`. — [Kiro steering](https://kiro.dev/docs/steering/)
- Windsurf workflows = Markdown files (title, description, steps), invoked manually as `/name` only (never auto-invoked; automatic behaviour is the job of Skills); 12,000-char limit per file; can call other workflows by name. — [Windsurf/Devin workflows](https://docs.devin.ai/desktop/cascade/workflows)
- MCPB (MCP bundle) manifest v0.3: required `manifest_version`, `name`, `version` (semver), `description`, `author`, `server`; `server.type` node/python/binary/uv; `mcp_config` {command,args,env, platform_overrides}; `user_config` (string/number/boolean/directory/file, sensitive, required, default); `tools`/`prompts` static lists; `compatibility` (client versions, platforms, runtimes). Substitutions `${__dirname}`, `${user_config.KEY}`. Claude Code plugins can reference `.mcpb`/`.dxt` bundles (extracted into `.mcpb-cache/`). — [MCPB MANIFEST.md](https://github.com/modelcontextprotocol/mcpb/blob/main/MANIFEST.md), [plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)
- MCP Registry: `server.json` metadata (reverse-DNS name like `io.github.user/server`, where to fetch the package e.g. npm, run args/env). The registry hosts metadata only, points to npm/PyPI/Docker; no private servers; in preview. — [MCP Registry about](https://modelcontextprotocol.io/registry/about)
- Home Assistant blueprints: an automation/script/template config with parts left blank to fill in; every instance is independent and "inherits from the blueprint"; edits to a blueprint propagate to instances on reload; shared via community forum. — [HA blueprints](https://www.home-assistant.io/docs/blueprint/)
- [BG, unverified] Goose recipes: YAML (title, description, instructions, prompt, parameters, extensions, sub_recipes, settings). Cline: `.clinerules/` folder of Markdown rules; Roo modes derived from Cline. Zed: agent profiles in settings.json (tool allowlists), `.rules` file plus AGENTS.md/CLAUDE.md compat, extensions package slash commands/MCP servers/themes/languages with `extension.toml`. Aider: CONVENTIONS.md loaded via `--read`. OpenHands: microagents/skills as Markdown with frontmatter (triggers) in `.openhands/`. Warp Workflows: YAML with templated args, shared via Drive/repo. Raycast: TypeScript extensions in a store; AI Commands/presets as JSON/deeplinks. Obsidian: community plugin = `manifest.json` + `main.js` + `styles.css`; Templater templates are plain Markdown. n8n/Dify/Langflow: JSON (n8n) or YAML/JSON (Dify DSL, Langflow) flow export/import. GitHub Actions: `action.yml` + reusable workflows (`workflow_call`). Apple Shortcuts: signed `.shortcut` files via iCloud links.

### Inferences
- Common denominator for Carbon: a workflow package = folder with a manifest (name, version, description, author, license, minimum Carbon version) + Markdown-with-frontmatter instruction files + optional MCP/hook/command files; this mirrors Claude Code plugin layout and keeps AGENTS.md/SKILL.md/.mcp.json reusable unchanged.
- Treat the Markdown-with-frontmatter file as the lowest-friction unit and the JSON/TOML manifest as optional (Claude Code works with no manifest), so a user can drop one `.md` file into a folder to create a workflow.
- A Carbon workflow (panel layout + commands + menus) has no direct analogue in these products; layout/menu declarations would be Carbon-specific manifest fields. Unknown fields should be ignored (skills) or stripped (plugin top level) rather than fatal, except in strict sub-objects, which is the precedent in Claude Code.

### Gaps
- Not fetched: VS Code custom-agent file reference, Cursor modes/commands, Cline, Warp, Aider, OpenHands, Goose, Raycast, Obsidian, n8n/Zapier/Make, Dify/Langflow, GitHub Actions, Apple Shortcuts, Zed extension manifest, Kiro hooks/specs, Open Plugins standard. Only [BG] lines above.

## Q2. Scopes and override layers; modifying a built-in without forking

### Takeaway
Nearly all products use enterprise/managed > user > project (or project > global) layers, but the direction differs per product, and most resolve same-name collisions by whole-file replacement, not property merge. Users modify built-ins by shadowing the same name/slug at a higher layer (Roo, Windsurf) or by a settings-level override switch (Claude Code `skillOverrides`), so no fork is needed.

### Cited Findings
- Claude Code settings precedence (highest first): Managed, command line, project local (`.claude/settings.local.json`), shared project (`.claude/settings.json`), user (`~/.claude/settings.json`); a higher level overrides the same key. — [Claude Code settings](https://code.claude.com/docs/en/settings)
- Claude Code skills locations: enterprise (managed dir), personal `~/.claude/skills/`, project `.claude/skills/`, nested `<subdir>/.claude/skills/`, plugin `<plugin>/skills/`. Collision precedence: enterprise > personal > project. Plugin skills are namespaced (`/plugin:skill`) so they do not collide. A skill replaces a bundled command of the same name; a skill beats a same-named `.claude/commands/` file. — [Claude Code skills](https://code.claude.com/docs/en/skills)
- Claude Code `skillOverrides` in settings sets a skill to `on`, `name-only`, `user-invocable-only` or `off` without editing the skill file; edits to SKILL.md hot-reload in-session; `/reload-skills` after creating a new skills dir. — [Claude Code skills](https://code.claude.com/docs/en/skills)
- Claude Code plugin install scopes: user, project (`--scope project`, in `.claude/settings.json`), local, managed; managed `enabledPlugins` force-enables/blocks and cannot be overridden by lower scopes; a managed marketplace entry replaces a same-name lower-precedence entry with no field merge. — [Org plugin management](https://code.claude.com/docs/en/plugins/org)
- Claude Code plugin content cache: `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`; `${CLAUDE_PLUGIN_ROOT}` changes on update so state must go in `${CLAUDE_PLUGIN_DATA}` (`~/.claude/plugins/data/<id>/`), which survives updates and is deleted on uninstall of the last scope unless `--keep-data`. — [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference), [Plugin security](https://code.claude.com/docs/en/plugins/security)
- Roo Code: project `.roomodes` > global `custom_modes.yaml` > defaults; same slug in project replaces the global mode entirely (no property merge). Overriding a built-in mode = define a mode with the built-in slug (e.g. `code`). Mode rules directory beats single-file fallback. — [Roo custom modes](https://roocodeinc.github.io/Roo-Code/features/custom-modes)
- Windsurf workflow name collision order: System (enterprise, OS dirs like `C:\ProgramData\Devin\workflows\`) > Workspace > Global (`~/.codeium/windsurf/global_workflows/`) > Built-in (e.g. `/plan`). Workspace discovery scans subdirs and parents up to git root; duplicates collapse to shortest relative path. — [Windsurf/Devin workflows](https://docs.devin.ai/desktop/cascade/workflows)
- Cursor rule precedence: Team Rules > Project Rules > User Rules; all applicable rules merge, earlier sources win on conflict; admins can enforce a team rule so users cannot disable it. — [Cursor rules](https://cursor.com/docs/context/rules)
- Kiro: global `~/.kiro/steering/` and workspace `.kiro/steering/`; workspace wins on conflict; teams can distribute global steering via MDM/Group Policy. — [Kiro steering](https://kiro.dev/docs/steering/)
- VS Code custom agents locations: workspace `.github/agents` (also reads `.claude/agents`), user `~/.copilot/agents` or `~/.claude/agents` (harness-dependent) or VS Code profile storage, org-level agents from GitHub org, extension/plugin-contributed agents. Agent instructions are added to custom instructions and take precedence on conflict; if `tools` is set only those tools are available. Docs do not state same-name precedence. — [VS Code custom agents](https://code.visualstudio.com/docs/copilot/customization/custom-agents)
- Claude Code plugin `name` conflicts: `--plugin-dir` copy vs managed `enabledPlugins` is covered under "Name conflicts" on the loading page (not fetched); settings `strictPluginOnlyCustomization` can block non-plugin skills/agents/hooks/MCP. — [Org plugin management](https://code.claude.com/docs/en/plugins/org)

### Inferences
- Carbon layering proposal consistent with all sources: built-in < user < project < managed(optional); namespace third-party workflows by package id (as `plugin:skill`) so collisions are structurally impossible; allow explicit same-id shadowing only for built-ins.
- "Modify a built-in without forking": offer (a) override-by-id file in user/project dir (whole-file replace, Roo/Windsurf style) and (b) a small settings-level override table (enable/disable/hide/rename, Claude `skillOverrides` style). Whole-file replace is simpler and predictable; merge semantics add bugs.
- Keep plugin state in a separate data dir from the (replaceable, versioned) install dir.

### Gaps
- Windows/macOS exact managed-dir paths for Claude Code not captured here. Cline/Cursor commands/custom modes precedence not verified. Zed profile precedence not verified.

## Q3. Permissions, trust, supply-chain and prompt-injection incidents

### Takeaway
Installing a plugin is treated as arbitrary code execution; products rely on a trust warning, source allowlists, version/SHA pinning and org policy, not sandboxing of plugin code. Weakest layer is community skill registries, where large-scale malicious-skill campaigns were documented in early 2026.

### Cited Findings
- Claude Code docs state a plugin "can execute arbitrary code on your machine with your user privileges". Hooks, monitors, MCP/LSP server processes and mods run outside the sandbox and are not covered by permission rules; Claude's tool calls to plugin MCP tools or `bin/` executables are covered by permission rules. Skills/commands/agents enter context as instructions. Installing also enables the plugin unless `defaultEnabled:false`. — [Plugin security](https://code.claude.com/docs/en/plugins/security)
- Trust UX: warning before install ("Anthropic does not control what MCP servers, files, or other software are included in plugins..."), `/plugin` details pane "Will install" component list (shows a hook exists, not what it runs), `claude plugin details` inventory, org can append `pluginTrustMessage`. Auto-update can change reviewed files on disk. — [Plugin security](https://code.claude.com/docs/en/plugins/security)
- Marketplace name tiers: official/community names accepted only if sourced from `github.com/anthropics/`; community catalog pins nearly every plugin to a commit SHA and Claude Code refuses a different commit; `archive` sources can pin a `sha256` digest and install fails on mismatch. Reserved plugin names (`claude-*`, `anthropic-*`) fail validation. — [Plugin security](https://code.claude.com/docs/en/plugins/security), [manifest reference](https://code.claude.com/docs/en/plugins-reference)
- Org controls: `strictKnownMarketplaces` allowlist (github repo, owner wildcard, git, url, hostPattern, pathPattern; `[]` locks everything), `blockedMarketplaces`, `enabledPlugins:false` blocks per plugin, `disableSideloadFlags`, `disableCommandPluginSources`, `allowManagedHooksOnly`, `strictPluginOnlyCustomization`. Allowlist matches marketplace source, not entries inside it. Project `extraKnownMarketplaces` apply only after the workspace trust dialog. — [Org plugin management](https://code.claude.com/docs/en/plugins/org)
- Skill-level permissions in Claude Code: `allowed-tools` pre-approves tools only during the skill turn; `Skill(name)` permission rules allow/deny skills; `disallowed-tools`. In the open standard `allowed-tools` is experimental and varies by agent. — [skills](https://code.claude.com/docs/en/skills), [spec](https://agentskills.io/specification)
- Roo: mode `groups` restrict tool categories and `edit` + `fileRegex` restricts writable paths (violations raise `FileRestrictionError`). VS Code: restricting `tools` in an agent limits capability; docs advise least privilege and read-only tools for sensitive workflows when sharing. — [Roo](https://roocodeinc.github.io/Roo-Code/features/custom-modes), [VS Code](https://code.visualstudio.com/docs/copilot/customization/custom-agents)
- MCP Registry security: namespace authentication (GitHub/DNS/HTTP challenge) proves who published; scanning delegated to package registries and aggregators; maintainers can take down spam/malicious entries. — [MCP Registry about](https://modelcontextprotocol.io/registry/about)
- Snyk "ToxicSkills" (published 2026-02-05): of 3,984 skills scanned from ClawHub and skills.sh, 36.82% had at least one security flaw, 13.4% had a critical issue, 76 confirmed malicious payloads (8 still live at publication); 91% of confirmed malicious skills used prompt injection; techniques: install instructions fetching password-protected ZIP malware, base64/Unicode-obfuscated exfiltration, disabling security settings, backdoors; 10.9% of ClawHub skills had hardcoded secrets. — [Snyk](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub/)
- Search-result summary (secondary, figures conflict): Koi Security counted 341 malicious of 2,857 skills, later "ClawHavoc" campaign reportedly 1,184 confirmed; Atomic macOS Stealer payloads reported by Trend Micro; OWASP Agentic Skills Top 10 lists malicious skills as AST01; CVE-2025-59536 (CVSS 8.7, repository-controlled config leading to command execution, patched in Claude Code 1.0.111) is mentioned; Anthropic reportedly added detection of invisible Unicode Tag characters in context files. — [Search aggregate](https://owasp.org/www-project-agentic-skills-top-10/ast01.html), [CSA note](https://labs.cloudsecurityalliance.org/research/briefing-csa-research-note-skill-md-agent-context-poisoning/), [Lakera](https://lakera.ai/blog/the-agent-skill-ecosystem-when-ai-extensions-become-a-malware-delivery-channel); numbers differ by source and were not independently verified.

### Inferences
- Carbon (stated "secure-by-default") should not copy the "trust warning only" model: hooks/MCP servers/scripts from a workflow package should run under the OS sandbox and capability grants (as already planned for WASM), with the manifest declaring requested capabilities (paths, network, tools, spawn) shown at install and diff-reviewed on update.
- Prompt-injection risk lives in the Markdown body itself (fake prerequisites, hidden Unicode); a Carbon installer should strip/flag invisible Unicode, show raw file contents, and never auto-run `scripts/` or shell-injection syntax at install.
- Pin by commit SHA/hash and disable silent auto-update for third-party packages; offer source allowlist (org policy) from day one, mirroring `strictKnownMarketplaces`.
- Project-scoped workflows (from a cloned repo) must require a workspace-trust gate before enabling hooks/MCP (Claude Code gates project marketplaces on the trust dialog).

### Gaps
- Primary-source Koi/ClawHavoc/CVE details not fetched (secondary only). No incident data found for Cursor, VS Code agents, Cline/Roo marketplace, Open VSX in this session. Signing: MCPB page does not mention signing; no signing scheme found for Claude plugins (only SHA/sha256 pinning).

## Q4. Dependencies between components/bundles, and behaviour when missing

### Takeaway
Bundles declare components by directory convention or manifest path, not by a dependency solver, with the exception of Claude Code plugin `dependencies` (plugin-to-plugin, semver ranges resolved against git tags). Missing or disabled dependencies disable the dependent plugin with an error rather than failing silently.

### Cited Findings
- A single Claude Code plugin can bundle skills, commands, agents, hooks, MCP servers, LSP servers, output styles, monitors, themes, `bin/` executables and default settings, installed and enabled as one unit. — [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)
- Plugin `dependencies`: array of `"name"`, `"name@marketplace"` or `{name, marketplace, version}` where `version` is a semver range (`~2.1.0`, `^2.0`); resolves to highest git tag `<plugin>--v<version>`; unconstrained deps track the latest. Multiple constraints intersect (highest satisfying all); incompatible ranges fail with "conflicting version requirements"; no satisfying tag fails the install (own-repo plugin) or checks at load (relative path). — [Plugin dependencies](https://code.claude.com/docs/en/plugins/dependencies)
- Missing/disabled dependency: plugin is disabled with error `... is disabled - enable it or remove the dependency`; cross-marketplace deps are refused unless root marketplace lists the target in `allowCrossMarketplaceDependenciesOn` (prevents one marketplace silently pulling plugins from an unreviewed source); `command`-source deps are never auto-installed; `claude plugin prune` removes orphaned auto-installed dependencies. — [Plugin dependencies](https://code.claude.com/docs/en/plugins/dependencies)
- A plugin with only `name` + `dependencies` is a valid "bundle" plugin (meta-package) to install curated sets with one command. — [Plugin dependencies](https://code.claude.com/docs/en/plugins/dependencies)
- `userConfig` prompts the user at enable-time (string/number/boolean/directory/file; `sensitive` values go to the OS credential store; substituted into MCP/LSP config as `${user_config.KEY}` and exposed to hooks as `CLAUDE_PLUGIN_OPTION_<KEY>`; not allowed in shell-form hook commands to avoid injection). — [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)
- Plugin-declared MCP servers load from `.mcp.json` first, then manifest-declared shapes; later same-named server replaces earlier; `claude plugin validate` flags undeclared `${user_config.*}` refs and non-loopback `http://` URLs. — [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)
- Agent Skills `compatibility` field is free-text environment requirements (e.g. "Requires git, docker, jq"); nothing enforces it in the spec. — [agentskills.io spec](https://agentskills.io/specification)
- MCPB `compatibility` has machine-checkable client version, platforms and runtimes; `user_config` collects secrets/paths. — [MCPB MANIFEST.md](https://github.com/modelcontextprotocol/mcpb/blob/main/MANIFEST.md)
- Kiro custom agents must opt in to steering files via `resources`; Claude `settings.json` in a plugin only applies `agent` and `subagentStatusLine`, other keys are dropped (components cannot silently change arbitrary host settings). — [Kiro steering](https://kiro.dev/docs/steering/), [manifest reference](https://code.claude.com/docs/en/plugins-reference)

### Inferences
- Carbon manifest should have: `requires.carbon` (version range), `requires.mcp` (server ids or inline definitions), `requires.workflows/skills` (id + semver), `requires.capabilities` (network/fs/spawn), `user_config`. Missing dependency policy: package installs but stays disabled with a visible reason in Manage Workflows, with one-click "install dependency" (never silent cross-source install).
- Reserve a plugin-owned data dir and keep manifest-level host-setting injection to a tiny allowlist (Claude's precedent) so an installed workflow cannot break other workflows or global settings.
- Layout/menu/command contributions should be declarative with unique namespaced ids (`pkg:command`) so removal is a clean unregister.

### Gaps
- Behaviour on missing MCP servers declared by skills (not plugin-level) is not documented in fetched sources. Open Plugins spec, VS Code extension-contributed chat participants, Zed extension dependency model not researched.

## Q5. Sharing, install, versioning/updates, enable/disable/remove

### Takeaway
Distribution is dominated by git: the repo is the registry (marketplace.json in a git repo, `.github/agents`, `.kiro/steering`, `.roomodes`), with optional curated directories and one-click marketplaces on top. Updates are either pinned (explicit version / SHA) or follow the branch head with background auto-update.

### Cited Findings
- Claude Code: `claude plugin marketplace add <owner/repo|path|url>` registers a catalog; `claude plugin install name@marketplace [--scope user|project|local]`; `/plugin` UI; `claude plugin list/details/uninstall/validate/tag/prune`; local dev with `--plugin-dir` and `/reload-plugins`. Share one plugin without marketplace by sending directory or zip. — [Create a marketplace](https://code.claude.com/docs/en/plugin-marketplaces)
- Versioning: setting `version` in plugin.json pins users to that version until it changes (not validated as semver); without it the install is keyed by commit (per the loading page, not fetched); `claude plugin tag --push` creates `<name>--v<version>` tags after validation; release channels = two marketplaces pointing at different refs. — [manifest reference](https://code.claude.com/docs/en/plugins-reference), [dependencies](https://code.claude.com/docs/en/plugins/dependencies), [org](https://code.claude.com/docs/en/plugins/org)
- Auto-update is per marketplace (managed `autoUpdate` true/false; `DISABLE_AUTOUPDATER`), old versions kept 14 days after uninstall before sweep; `enabledPlugins` entry persists across updates (changing `defaultEnabled` later does not affect existing users). Seed dirs (`CLAUDE_CODE_PLUGIN_SEED_DIR`) provide read-only offline plugin sets for containers. — [Plugin security](https://code.claude.com/docs/en/plugins/security), [manifest reference](https://code.claude.com/docs/en/plugins-reference), [org](https://code.claude.com/docs/en/plugins/org)
- Enable/disable/remove: `enabledPlugins` map in settings by scope (true/false), `claude plugin disable`, uninstall per scope, remove marketplace (uninstalls all its plugins); managed false hides plugin; disabled-in-user-but-forced-by-managed is surfaced in `/plugin`. — [org](https://code.claude.com/docs/en/plugins/org), [security](https://code.claude.com/docs/en/plugins/security)
- Roo: marketplace one-click mode install; export/import of modes plus rules as one YAML file, choose Project/Global on import; importing a matching slug overwrites; slug editable before import; new mode may need window reload. — [Roo custom modes](https://roocodeinc.github.io/Roo-Code/features/custom-modes)
- Cursor: shareable rules arrive through plugins published via a marketplace (not as standalone files); team rules via dashboard. — [Cursor rules](https://cursor.com/docs/context/rules)
- VS Code: team sharing by committing agents to `.github/agents`; cross-repo via org-level agents (setting `github.copilot.chat.organizationCustomAgents.enabled`); extension-provided agents cannot be deleted in the UI, only by disabling/uninstalling the extension. — [VS Code custom agents](https://code.visualstudio.com/docs/copilot/customization/custom-agents)
- Windsurf: workspace workflows committed to repo; global ones in user dir not shared; enterprises deploy system-level workflows to OS directories. — [Windsurf/Devin workflows](https://docs.devin.ai/desktop/cascade/workflows)
- Home Assistant: share by URL import and community forum; instances inherit blueprint updates on reload. — [HA blueprints](https://www.home-assistant.io/docs/blueprint/)
- MCP Registry: publish-once metadata with DNS/GitHub-verified namespace; clients should consume via downstream aggregators implementing the registry OpenAPI; official codebase not designed for self-hosting. — [MCP Registry about](https://modelcontextprotocol.io/registry/about)

### Inferences
- For Carbon Manage Workflows: install sources = (1) local folder/zip, (2) git URL (pinned to tag/SHA), (3) a catalog JSON like marketplace.json (own gallery) — all landing in one user dir `workflows/<id>/<version>/` plus a data dir; project-level enabling by committing a small settings file (like `enabledPlugins`), gated by workspace trust.
- Enable/disable must be a state flag separate from files so uninstall is optional and built-ins can be disabled but not deleted.
- Honour existing conventions as a compatibility layer: read SKILL.md folders, AGENTS.md, `.mcp.json` from project and user dirs, and accept Claude-Code-shaped plugin folders as importable workflows (low cost, high ecosystem reach).
